# AI開発ワークフロー

## 1. この文書の目的

この文書は、GogmaArtianPlannerで複数のAIコーディングエージェントを利用する際の共通運用を定義する。

対象は以下とする。

- タスク準備
- 実装担当AIの選定
- AI間の作業引き継ぎ
- Working Treeの保護
- 実装後の検証
- 設計レビュー
- commit / pushの扱い

この文書は開発運用ガイドであり、製品仕様・Domain仕様ではない。

仕様権威は `AGENTS.md` の定義に従い、この文書はそれを上書きしない。

---

## 2. 役割

### プロジェクトオーナー

最終判断はプロジェクトオーナーが行う。

対象には以下を含む。

- 製品仕様・Domain仕様の決定
- 仕様変更を行うかどうか
- 実装内容を受け入れるかどうか
- commit / pushを行うかどうか
- 外部サービス、認証情報、破壊的操作の承認

### ChatGPT設計チャット

プロジェクトの設計チャットは主に以下を担当する。

- タスク内容の整理
- 影響する仕様の確認
- 仕様決定が必要かどうかの判断
- 実装担当AIの選定
- 実装指示の作成
- 実装後diffのレビュー
- 追加修正が必要かどうかの判断

設計チャットの判断はRepository内の正式仕様を置き換えない。

### コーディングエージェント

実装タスクは原則として以下のいずれかに割り当てる。

- Codex Terra
- Codex Sol
- Claude Code

選定されたエージェントは、依頼された範囲のみを実装し、`AGENTS.md`、関連する仕様書、本ワークフローに従う。

---

## 3. 実装担当AIの選定

実装開始前に、タスクごとに担当AIを選定する。
原則としてタスク開始時に担当AIを決定し、実装途中のAI交代は例外とする。

以下はプロジェクト運用上の初期基準であり、各モデルの恒久的な能力評価を意味しない。

### Codex Terra

次のような作業で優先する。

- 仕様が確定している小～中規模の実装
- 局所的なUI / Application変更
- 単純なテスト追加
- レビュー指摘に対する機械的な修正
- タスク遂行に直接必要な小規模リファクタリング

### Codex Sol

高い推論負荷またはDomainリスクがある作業で優先する。

例:

- 文書化済みDomain契約へ影響する可能性がある変更
- Production RNG semantics
- Planner / Searchの重要な不変条件
- 複数レイヤーを跨ぐArchitecture変更
- 原因特定が難しい不具合調査
- 影響範囲の大きいコードレビューや設計検証

RNGやPlannerのファイルを触るだけで自動的にSolを選ぶわけではない。
仕様が確定しており機械的な変更であれば、TerraまたはClaude Codeも候補とする。

### Claude Code

次のような場合に優先する。

- 仕様が安定しており、Repository全体を参照しながら実装する作業
- Codexの使用可能量や追加クレジット消費を抑えたい場合
- 多数のファイルを横断して確認・編集する作業
- Codexの使用量上限によって中断したタスクを、やむを得ず引き継ぐ場合

Claude Codeは、仕様未確定タスクの自動的な代替手段ではない。
仕様判断が必要な場合は、実装前に設計チャットで決定する。

### 選定時の判断材料

設計チャットでは少なくとも以下を考慮する。

1. Domain契約を壊した場合の影響
2. 仕様の確定度
3. 変更規模と影響範囲
4. 調査・推論の難度
5. Codexの残り使用可能量とコスト
6. 途中交代が必要になった場合の引き継ぎコスト
7. 実装後レビューの負荷

固定表よりも、タスク固有の判断を優先する。

## 4. タスク間の基準状態

完了したタスクがcommit / push済みの場合、通常はpush済み `main` を次タスクの設計基準とする。

一方、実装中は未commit / 未pushのローカルWorking Treeが最新状態である。

ローカル変更が存在する場合、GitHubだけを見て最新状態だと判断しない。

remoteの状態へ合わせるためだけに、勝手にpull、rebase、resetその他のWorking Treeを書き換える操作を行わない。

---

## 5. タスク開始時の確認

実質的な編集を始める前に、コーディングエージェントは以下を行う。

1. `AGENTS.md` を読む
2. `docs/REQUIREMENTS.md` を読む
3. `AGENTS.md` が要求するタスク関連仕様を読む
4. 関連する実装とテストを確認する
5. 依頼範囲と明示された対象外を確認する
6. 現在のGit状態を確認する

最低限、以下を確認する。

```bash
git status --short
git diff
git diff --cached
git log -1 --oneline
```

Working Treeがcleanでない場合、現在のタスク開始前から存在する変更かどうかを確認してから編集する。

既存変更を不要なものと決めつけない。

---

## 6. Working Treeの保護

既存ローカル変更は以下のいずれかである可能性がある。

- プロジェクトオーナーの作業
- 前任コーディングエージェントの作業
- 別タスクの未完了作業
- 使用量上限などで中断した現在タスクの作業

プロジェクトオーナーが明示的に破棄を許可しない限り、それらを保持する。

明示的な承認なしに、既存作業を失わせる以下のような操作を行わない。

```text
git reset --hard
git restore <path>
git checkout -- <path>
git clean
既存作業を破棄するための強制的なbranch差し替え
既存作業を失わせるhistory rewrite
```

無関係な既存変更を勝手にstashして隠さない。

既存変更と新しいタスクが衝突する場合は、

1. 衝突箇所を特定する
2. 内容を報告する
3. 安全な範囲の作業は継続する
4. 他者の作業を破棄・書き換える前に判断を求める

---

## 7. AI間の引き継ぎ

別のAIまたはプロジェクトオーナーが開始した作業を続ける場合、引き継ぎとして扱う。

引き継ぎ先エージェントは、実装を続ける前に以下を行う。

1. タスク開始時のGit確認を行う
2. 元のタスク指示を読む
3. 関連仕様を読む
4. 現在のdiffと関連テストを確認する
5. 引き継いだ作業を以下に分類する
   - 完了済み
   - 未完了
   - 判断不能
   - 失敗中 / 未検証
6. 大きな追加編集を始める前に、残作業を簡潔に整理する

前任エージェントの実装を正しいものと決めつけない。
仕様とテストで検証する。

一方、別エージェントが作業していたという理由だけで最初から作り直さない。

既存変更を置き換える場合は、具体的な理由があり、かつユーザーや別タスクの無関係な変更を失わせないことを確認する。

引き継ぎ時に有用な情報:

- 元のタスク指示
- 現在branchと基準commit
- `git status --short`
- unstaged / staged diff
- 前任エージェントの完了・中断報告
- 関連仕様
- 既知の失敗テスト、または未実行の検証

---

## 8. 実装時の基本ルール

依頼されたタスクへ集中する。

Architecture、Domain、RNG、Search、Planner、Persistence、UI、Worker、Testingに関するルールは `AGENTS.md` に従う。

追加で以下を守る。

- 関連コードを調査してから変更する
- 将来機能を推測して追加しない
- タスク外のついで修正を行わない
- 不要な抽象化や過剰設計を避ける
- 調査用の一時ファイルやスクリプトは不要になったら削除する
- テストを通すためだけにテストを弱めない
- unexpected failureをsupported / no-matchへ変換しない
- 未確認のゲーム挙動や製品要件を発明しない

仕様不足が判明した場合は、推測せず `AGENTS.md` の仕様矛盾・不足時の手順に従う。

---

## 9. 検証

必要に応じてタスク固有テストを先に実行する。

タスク完了前には、`AGENTS.md` が要求する標準チェックを実行する。

```bash
npm run lint
npm test
npm run build
```

加えて以下を実行する。

```bash
git diff --check
git status --short
```

専用type-check commandが存在し、`AGENTS.md` 上必要な場合はそれも実行する。

実際に実行していないコマンドを「成功した」と報告しない。

必要なコマンドを実行できない場合は、

- 実行していないコマンド
- 実行できなかった理由
- 代わりに行った確認

を報告する。

完了報告前に最終diffを確認し、以下が混入していないことを確認する。

- 意図しないファイル
- 無関係なリファクタリング
- 不要な生成物
- タスクで要求されていない仕様変更
- debug / temporary code

---

## 10. レビューループ

通常の開発ループは以下とする。

```text
ChatGPT設計チャット
  -> タスク / 仕様決定
  -> 実装担当AI選定
  -> 実装
  -> 検証
  -> diffを設計チャットへ戻す
  -> 設計レビュー
  -> 必要なら追加修正
  -> プロジェクトオーナーがcommit / pushを判断
```

設計レビューでは主に以下を確認する。

- 依頼範囲を満たしているか
- 仕様に整合しているか
- Domain invariantを保持しているか
- 意図しない挙動変更がないか
- テストが十分か
- 未解決事項が明確か

コーディングエージェントの完了報告だけで最終承認とはしない。

---

## 11. commit / push

原則として、明示指示がない限りcommit / pushしない。

タスク指示またはプロジェクトオーナーが明示的に要求した場合のみ実施する。

commitする場合:

- レビュー対象タスクだけを含める
- 無関係なローカル変更を混ぜない
- 特別な指示がない限りcommit messageは日本語にする
- commit SHAを報告する

明示的な承認なしにforce pushしない。

---

## 12. 完了報告

完了報告は `AGENTS.md` の要件に従う。

加えて以下を報告する。

- タスク開始時にWorking Treeがcleanだったか
- 引き継ぎ変更が存在したか
- 引き継ぎ変更を修正したか
- `git diff --check` の結果
- commit / pushを実施したか

簡潔かつ事実ベースで記載する。

---

## 13. この文書を変更する場合

この文書は、AIを利用した開発運用そのものが変わった場合だけ更新する。

製品要件、RNG契約、Planner挙動その他のDomain仕様はここへ記載しない。

それらは `AGENTS.md` が示す正式仕様書へ記載する。
